# Graphwake example services

Two small example APIs that show a [Graphwake](https://graphwake.com) setup with both kinds of spec source:

- **`catalog`**: Graphwake fetches its OpenAPI document from a URL.
- **`orders`**: the document is uploaded from GitHub Actions by the [Graphwake CI agent](https://github.com/graphwake/agent).

This repository also **changes itself twice a day**. The Graphwake team watches these two services from a production
workspace: every change should end in an e-mail, so a missing e-mail means something in the pipeline is broken.

There is no running server: the services exist only as OpenAPI documents.

## The services

| Service | Spec | Graphwake source | Endpoints | Watched endpoint |
|---|---|---|---|---|
| `catalog` | [`services/catalog/openapi.json`](services/catalog/openapi.json) | URL | `GET /products`, `GET /products/{id}`, `GET /categories`, `GET /categories/{id}` | `GET /products/{id}` |
| `orders` | [`services/orders/openapi.json`](services/orders/openapi.json) | CI | `GET /orders`, `POST /orders`, `GET /orders/{id}`, `POST /orders/{id}/cancel` | `GET /orders/{id}` |

`orders` uses products from `catalog`: an order line carries a `Product`. `orders` keeps its own copy of the `Product`
schema with the same name on purpose. Graphwake's Discovery uses matching schema names as a signal when it suggests
which teams consume an endpoint.

The documents are generated by [`scripts/specs.mjs`](scripts/specs.mjs). Don't edit them by hand: the tests fail when a
document doesn't match [`state.json`](state.json).

## How the repository changes itself

The [Change the specs](.github/workflows/mutate.yml) workflow runs at **09:00 and 15:00 Europe/Istanbul** (06:00 and
12:00 UTC). GitHub can start scheduled runs some minutes late. Each run applies the next step of a four-step cycle to
the watched endpoint of both services:

| Step | Change | Breaking? |
|---|---|---|
| 1 | Add an optional response field (`ProductDetail.warrantyMonths`, `OrderDetail.giftNote`) | No |
| 2 | Remove that field | Yes |
| 3 | Remove the watched endpoint | Yes |
| 4 | Restore the watched endpoint | No |

After step 4 the documents are back where they started, so the cycle repeats every two days. `state.json` records the
last step applied, and the commit message names the change.

The run commits to `main` and then starts [Upload orders spec to Graphwake](.github/workflows/upload-orders.yml) as a
separate run. They are kept apart because the agent only sends the spec of the branch's newest commit, and a run that
pushes a new commit is no longer building the newest one.

To change the specs by hand: **Actions → Change the specs → Run workflow**.

## Set it up in your Graphwake workspace

1. **Create the `catalog` service** with a **URL** source:
   `https://raw.githubusercontent.com/graphwake/example-services/main/services/catalog/openapi.json`
   Graphwake checks it every 30 minutes.
2. **Create the `orders` service** with a **CI** source. Copy its ingest key into this repository's secrets as
   `GRAPHWAKE_KEY` (Settings → Secrets and variables → Actions).
3. **Subscribe a team** to `GET /products/{id}` and `GET /orders/{id}`, and turn on **All changes** in the team's Notifications
   tab. With breaking changes only, steps 1 and 4 send nothing.
4. **Add yourself to that team.**

To send your own service's spec from CI, copy [`.github/workflows/upload-orders.yml`](.github/workflows/upload-orders.yml)
and point `spec` at your document. The [agent's README](https://github.com/graphwake/agent#readme) covers pull request
builds and other CI platforms.

## What to expect

Every run sends **one e-mail per service**, so four e-mails a day:

- `orders`: within a few minutes of the run (CI upload).
- `catalog`: within about 30 minutes (the next URL check).

If an e-mail is missing, check in this order:

1. The **Change the specs** run: did it finish, and what does its summary say changed?
2. The **Upload orders spec to Graphwake** run: the agent prints one line saying what it sent, or why it sent nothing.
   The agent never fails the workflow, so a green run can still have sent nothing.
3. In Graphwake, the `catalog` service's last URL check and its status.
4. The team's subscriptions and its **All changes** setting.

GitHub turns off scheduled workflows in a repository with no activity for 60 days. The bot's commits count as
activity, so this should not happen while the workflow runs.

## Run locally

Requires Node 22. There are no dependencies.

```sh
npm test                    # generator and cycle tests
node scripts/mutate.mjs     # apply the next step to your working copy
git checkout -- .           # undo it
```
